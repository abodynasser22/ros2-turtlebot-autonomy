SAFETY_MARGIN = 0.02 m is added to every keep-out (it's also a parameter, safety_margin). It wasn't in the first version. It was added after the first s1a run, where the three-disc plank grazed the obstacle by 2 mm because odometry was 2.8 cm off the truth (§15, §16). With it, the gap each footprint needs becomes 2(r + 0.02): 0.579 m for one disc and 0.300 m for three.

sweep is the same for one and three because it describes the real plank, and it is only used to shrink the box. So the box treats both footprints identically and can't confound the comparison.

rectangle_clearance is Theory Guide §15's clamp formula. The controller never calls it. It sits here so the plank's size is written down in exactly one place, and the desk sim and analysis both import it.

9The node, part 6: starting and stopping

{{code|mpc_node.py| def stop|if __name__}}
Lab 2's main() called plain rclpy.init(). In Jazzy, Ctrl-C then makes rclpy's own signal handler shut the context down first, and the finally: node.stop() publish fails with "publisher's context is invalid". The robot is never told to stop. On a real TurtleBot it keeps its last command until the motor watchdog, if there is one. Found in the first headless run, where the node log ended in that exact traceback. SignalHandlerOptions.NO means Ctrl-C arrives as a plain KeyboardInterrupt, stop() publishes zero, and then we shut down.

12The evaluation harness

{{code|plot_run.py|def grade|def report}}
  • Clearance uses ground truth and the rectangle, never odometry and never discs (Theory Guide §15).
  • Path error is the distance from the true position to the reference curve, not to the moving reference point. That needs no clock alignment between the bag and the node's start time, and it measures what the eye sees: how far the robot left the line.
  • Goal reached means within 0.08 m of ground truth. The node stops at 0.05 m by odometry, and odometry sits 1–2 cm off truth in Gazebo, so 0.05 by truth would mark some correct stops as failures.
  • Pass (scenario 2): goal reached and clearance > 0 to every obstacle.
  • Reached in is timed from the first non-zero /cmd_vel, so Gazebo and node start-up aren't counted (a code-review fix: before it, 8.9 s read as 12.7 s).

13The node, part 7: things that move (scenarios 3 and 4)

Scenarios 1 and 2 only needed constants. Scenarios 3 and 4 need the node to know where something is now, and to write where it will be into the TVPs, one value per horizon step. Theory Guide §4 is the idea, §13 and §14 are the reasoning. This section is the code.

The two scenarios in the table

{{code|mpc_node.py|# Scenario 3: a cylinder crosses|CIRCLE = dict(}}
  • movers is a list of moving cylinders: start (x0, y0), velocity (vx, vy), radius. obstacles=[] because nothing is still. The goal is a fixed point, (2.0, 0.0), so the robot drives straight and the obstacle crosses its line at 4.0 s (1.2 m at 0.30 m/s).
  • target is the moving goal: a ball with a start and a constant velocity. goal='target' tells the node to chase it. The box is larger (y ±2.5 m) so the ball stays inside it for the whole run.
  • Gazebo, the node, the grader and the desk sim all read these entries. One table again.

Two small functions, shared with the desk sim

CodeWhat it means
if mode == 'now': return [(pos[0], pos[1])] * (steps + 1)The baseline. The same centre at every horizon step: the obstacle looks still. The controller reacts only when it is already close.
pos[0] + vel[0] * (delay_steps + k) * t_stepWith its future: a straight line at the known velocity. delay_steps + k because step 0 of the horizon is where the robot will be one tick from now (the node pushes its pose forward by delay_steps), so the obstacle is pushed forward by the same amount.
if mode == 'hold' or len(points) < 3The baseline for the goal: repeat the latest observation. Also the fallback, since a line needs at least three points.
t = np.asarray(times) - times[-1]Times measured back from the latest sample, so the latest is t = 0 and the fitted line's value at t = 0 is the estimate of where the ball is now.
tc = t - t.mean() and v = (tc * (p - p.mean)).sum / (tc**2).sumThe least-squares slope, Theory Guide §14, for x and y at once. Centring the times is what makes it this short.
now = p.mean(axis=0) - v * t.mean()The fitted line evaluated at t = 0. It is a smoothed position: with 2 cm of noise it is about 1.2 cm off instead of 2.
now + v * (delay_steps + k) * t_stepExtend the line over the horizon, shifted by the same delay as the obstacle.

They are plain functions with no ROS in them, which is why the desk sim could import them and why the numbers match between desk and Gazebo.

In the node: what is new in each tick

{{code|mpc_node.py| # ------------------------------------------------------------ moving things| def stop}}
Step in control_tickWhy it is there
world_ready()Nothing is solved until the pose of every moving thing has arrived. Without it, the first ticks would plan against an obstacle at (0, 0).

A pair differs in one node parameter. Both runs start the moving thing on the same tick, use the same code and the same noise seed. If future passes and now touches, the only possible reason is what was written into the TVP.
The node reads the obstacle's position from Gazebo and knows its velocity from the table. That is the proposal's assumption, "the obstacle follows a trajectory we choose, so we know its future and hand it over". A real robot would need a tracker for both. The robot's own pose still comes from /odom only.

How a moving obstacle is graded

The clearance is the same exact-rectangle formula as before (Theory Guide §15). What changes is the obstacle's centre: it is read from the bag's /mover_1/pose and interpolated to the time of every ground-truth sample of the robot, so the plank is always compared with the obstacle at that instant. The minimum over the run is reported together with the time it happened. A value of 0 or less is contact.

How a moving goal is graded

The distance between the robot's ground-truth position and the ball's ground-truth position, at every sample. Three numbers: when it first got within 0.2 m, the closest it got, and the mean over the last 5 s. Only the time the controller was commanding counts, from the first command to the last: the seconds after Ctrl-C would count a robot that has stopped against a ball that has stopped too.

16Silent failures we hit

Gate 1 task 3: the goal that never arrived. Two bags, 671 and 1307 /cmd_vel messages, every one exactly zero, and 0 predictions. /new_position is not even a topic in either bag, so the recorder never saw a publisher. Either the goal was published before the node existed (a ros2 topic pub message isn't stored for late subscribers), or from a terminal on another domain. How it was proved: same node and command, goal published 10 s after the node printed its first line, and the robot drove to (1.78, 0.01). Lesson: the node logs NEW GOAL. No such line means no goal, and nothing else will tell you.
"RViz shows nothing of the robot." The Lab 2 config has no display that draws the body: no RobotModel, and no marker for the footprint. Odometry arrows and TF axes are easy to miss. Fixed with a RobotModel display and /mpc_footprint. Verified by capturing the RViz window in a headless run: everything shows, with or without use_sim_time, so the clock was not the cause. A terminal on another domain would also give an empty RViz, so always check printenv ROS_DOMAIN_ID first.
Solve time tripled by a window. The first desk sweep gave a 118 ms median for Lab 2's own task. Your Gazebo GUI was still open. With it closed: 20–33 ms. Any solve-time number must say whether the GUI was running.
Ctrl-C didn't stop the robot. §9. Inherited from Lab 2, and invisible unless you read the node's last log lines.
The graze nobody saw coming. First s1a run with three discs: the desk simulation had predicted +3.7 mm of real clearance. At closest approach odometry was 2.7 cm off ground truth, and the real plank touched the obstacle (−2.1 mm, 18.6 s after the first command). Afterwards odometry drifted away from the truth, 0.22 m at 25 s and 1.03 m at the end, and the robot calmly tracked a circle in the wrong place for the rest of the lap. We did not test why the drift started. Every node log line looked fine. Only ground truth showed it. Lesson: a tighter footprint spends exactly the slack that used to absorb odometry error. Fix: a 2 cm safety margin, as Lab 3 did with its inflation radius.
Starting inside a keep-out. s1b's first obstacle position put the origin inside the one-disc keep-out. The soft constraint would have shoved the robot out, and the comparison would have measured that shove instead of the footprint. Caught by arithmetic before any run (LOG D2).
The recorder that died quietly. Scenario 3 and 4 runs were scripted. A background job in a non-interactive shell ignores Ctrl-C, so ros2 bag record never got its interrupt, had to be killed, and left a bag with data but no metadata.yaml. Nothing printed an error. run_headless.py resets the interrupt for every child and checks that metadata.yaml exists. Lesson: a recording is only a recording once ros2 bag info can read it.
A goal that proved nothing. The first moving goal drifted away slowly at 0.12 m/s. The robot is faster, so it catches up whatever it believes, and the fit and the hold gave 0.27 and 0.29 m. The ball also left the box before the run ended. Nothing was wrong with the estimator: the experiment could not show it. The geometry that works has the ball crossing the robot's path at 0.21 m/s. Lesson: before trusting a comparison, check that the situation can tell the two options apart.
Passing by a hair. At the desk, the controller with its future passed the obstacle with 1 to 2 cm of real clearance, about as close as the constraint allows. Odometry in Gazebo was 1.4 to 3.5 cm off in scenarios 1 to 3 (the largest error over a run), so that success would have been a coin flip. In Gazebo, with the extra keep-out, the real clearance came out at +0.048 to +0.056 m. 0.03 m of extra keep-out for moving obstacles moved the desk clearance to +0.044 m. Lesson: an optimiser uses every centimetre it is given, so give margin where there is uncertainty.
The window that counted a stopped robot. The first "mean distance over the last 5 s" for scenario 4 included the seconds after the node was stopped, when robot and ball are both standing still. Restricting it to the time the controller was commanding changed the numbers. Lesson: a metric needs a start and an end, and the bag keeps recording after the experiment ends.

17Things to try yourself

Each one is a single change, and each has a prediction you can check. Use the desk sim first (seconds), then Gazebo.

Make the slack cheap. -p obstacle_penalty:=10.0. Prediction: one disc starts squeezing through gaps it should reject, and real clearance drops. That shows why ρ must beat the tracking cost.
Longer horizon. -p n_horizon:=40 with gui:=false, and read /mpc_solve_time. Prediction: p95 near 170 ms on s2_030 three, over the tick. Watch whether the motion gets worse.
Turn delay compensation off. -p delay_steps:=0 on s1a. Lab 2 predicted more jerk with uncompensated delay. Compare the path error.
Tell the obstacle's future to nobody. Scenario 3 with -p prediction:=now. Prediction from the runs we have: contact at about 3.5 s, then the true heading and odometry's part ways and the robot ends about 1 m short of the goal. This is the half of the pair that fails.

Stop the noise. Scenario 4 with -p goal_noise:=0.0. Prediction: fit and hold both do better, and the fit gains less over the hold than with noise, since there is nothing to average. Then try -p goal_noise:=0.08: the fit should hold up much better than the hold, which follows every jump.
A shorter or longer window. -p fit_window:=0.4 and -p fit_window:=2.0. Prediction: the short window is noisier, the long window is smoother. For this straight-line ball both work, a ball that turned would punish the long one.
Speed up the obstacle. In SCENARIOS['s3'] change vy to −0.45. Prediction: it crosses earlier, the robot has less time, and with its future the clearance shrinks or it gives way sooner. Use the desk sim first: python3 desk/sim_scenario.py --scenario s3 --footprint three --prediction future --goal 2.0,0.0.
Take the margin away. -p safety_margin:=0.0. Prediction: three discs pass s2_028 again, and s1a three-disc grazes the obstacle again. The old bags in bags/margin0/ are exactly this experiment.

18Oral questions, with answers

Walk me through one control tick.Check odometry is fresh. Write the reference for each of the N+1 steps into the TVP. Push the measured pose forward by one tick using the last command (delay compensation). Call make_step, which solves the whole horizon with IPOPT. Time it and publish the time. If the solve failed, hold the last command for up to three ticks. Otherwise clip and publish the first input, and publish the predicted path.
How does the solver know where the plank is?It doesn't know about the plank. It knows three points, x + d·cos θ and y + d·sin θ for d ∈ {−0.167, 0, 0.167}, as CasADi expressions of the state, and it keeps each one at least ro + 0.130 from every obstacle centre.
How do you know the plank didn't hit anything?Gazebo's ground-truth pose, the exact 0.50 × 0.20 rectangle, and the clamp distance to each obstacle circle at every sample. The minimum over the run is reported. It's independent of both odometry and the disc model.
Why is the box soft? Isn't that unsafe?A hard bound on a measured state is unrecoverable once odometry puts you outside it: Lab 2 task 4. A linear penalty with ρ = 10⁴ is exact, so slack is zero whenever staying inside is possible. In scenario 2 the Gazebo walls are real, so any squeeze would show as contact in the ground-truth clearance.
Why N = 20 when you planned to measure 20, 40 and 60?We did measure. With the Gazebo window closed, N = 40 has a 95th-percentile solve of 174 ms on the hardest scenario, beyond the 100 ms tick. N = 20 has 59 ms. Its reach of 0.44 m is enough for scenarios 1 and 2, because every detour there is under 0.2 m.
What did three discs cost in computation?Read it from the solve-time column in §15: about 1.5× the median of one disc (33 against 22 ms), not 3×, because IPOPT's cost isn't proportional to the number of constraints.
What does the one-disc robot do at a gap it rejects?It drives up to where its 0.389 m keep-outs (0.10 + 0.269 + 0.02) meet the centreline and stops. The goal cost wants it forward, the slack cost (10⁴ per unit) forbids it, and the box forbids going round. That's a local minimum, the honest behaviour of a controller that believes it doesn't fit.
Where does odometry come from in Gazebo, and does it drift?From the diff-drive plugin, which integrates the simulated wheel motion. It drifts a little: 1–2 cm by the end of our runs, which is why we grade on ground truth.
Why one launch file, when Lab 1 and 2 said no launch files?Labs 1 and 2 used the course's own launch file for Gazebo. The project needs a world the course doesn't have (posts, walls, a robot with a plank, a ground-truth bridge). The launch file only does what turtlebot3_bringup does on the robot, and the controller still runs in its own terminal.
Why a 2 cm safety margin, and what did it cost?The first s1a run with three discs grazed the obstacle by 2 mm. Odometry was 2.8 cm off ground truth at that moment, and the three-disc plan left only about 4 mm of real clearance. 2 cm covers the measured error, and it's the same idea as Lab 3's inflation radius of 0.120 for a 0.105 robot. It cost 4 cm of gap: three discs now need 0.30 m instead of 0.26, so 0.28 is rejected. It still meets the proposal's 0.30 m.
What would you change for the real robot?Drop use_sim_time. Measure the actual actuation delay for delay_steps. There is no ground truth, so clearance would need a tape measure or a camera. And the plank would block nothing, since it sits above the lidar.
How does the controller know where the moving obstacle will be?It reads the obstacle's current position from Gazebo, and its velocity is in the scenario table because we chose the path. The future is a straight line: position now plus velocity times (delay_steps + k) time steps, for each horizon step k. That is the proposal's assumption. A real robot would need a tracker for both position and velocity.
What does the robot do when it knows the obstacle's future?It drives straight at 0.22 m/s until 1.8 s, about 2.2 s before the obstacle crosses its line and close to the 2.0 s horizon. Then it turns clockwise, brakes to a stop at x = 0.70 to 0.71 m at about 3.4 s, and keeps turning in place. Its heading is -61 degrees when the obstacle crosses at 3.98 s, with 0.08 to 0.09 m of clearance, and -90 degrees at 4.7 s, which puts the plank along the obstacle's direction of travel. The robot turns back and drives on at about 5 s, and reaches the goal in 11.4 to 11.5 s, against 8.9 s for the same drive past the open corridor of scenario 2. We expected it to wait, and it also turns. Our reading is that a plank lying along the obstacle's path is the cheapest way to keep the keep-out, and we did not test that.
Why is the clearance with its future only about 5 cm?It matches the margins. The keep-out is 0.28 m (obstacle 0.10, discs 0.130, margin 0.02, extra for moving 0.03), so with a disc centre exactly on the keep-out the surfaces are 0.28 − 0.10 − 0.130 = 0.05 m apart. We measured +0.048, +0.049 and +0.056 m. The solver has no reason to leave more room than the constraint asks for, and the real plank is inside the discs, so it can be a little more.
Why 0.03 m of extra keep-out for a moving obstacle?In the desk runs the controller that knew the future passed with 1 to 2 cm, and the largest odometry error over a run in Gazebo was 1.4 to 3.5 cm in scenarios 1 to 3, so passing would have been a coin flip. It is the same idea as the 2 cm margin: uncertainty about where things are goes into the keep-out.
What exactly goes wrong when the controller only knows where the obstacle is now?It sees a still obstacle and drives straight at 0.22 m/s. Its first reaction is at about 3.2 s, when the obstacle is 0.24 m from the robot's line. It brakes and begins to turn, and the plank touches the obstacle at 3.5 s (−6 to −8 mm, for 0.5 to 0.7 s). After that the true heading keeps turning clockwise, by 300 to 550 degrees over the run, while odometry's heading does not follow, so the controller steers from a pose that is wrong by about a metre. The robot stops 1.0 to 1.6 m short of the goal. We do not know why the true heading kept turning, and we did not test whether the wheels slipped. The symptom, odometry disagreeing with the truth after a contact, is the same as in the zero-margin graze of scenario 1.
How do you make sure the pair is fair?One node parameter differs. The obstacle and the ball are started by the node on its first control tick, so they start with the robot. The scenario table, the code and the noise seed are the same. The grading is from the ground truth, not from anything the controller believes.
Why fit a line to 10 points instead of using the last two?Noise. With 2 cm of noise and a tick of 0.1 s, the speed from two points has a standard deviation of about √2 · 0.02 / 0.1 = 0.28 m/s, more than the ball's speed (0.21 m/s). A least-squares line through 10 points has about 0.02 / √(Σ(t − t̄)²) = 0.02 / 0.91 = 0.022 m/s. The fitted position at the latest time is also about 1.2 cm off instead of 2 cm.
Why not a Kalman filter?For a straight line at constant speed, a least-squares fit over a short window does the same job and needs no model of the noise or the dynamics. A Kalman filter would be the next step for a goal that accelerates or turns: it can carry an acceleration state and weight old data by how much it can be trusted. We name it as the alternative and did not need it.
Why add noise to the ball's position at all?With exact positions the fit is almost the same as holding, and there is nothing for a fit to average out. A real tracker would give noisy positions, so 2 cm of Gaussian noise is a fair stand-in. Both runs of a pair use the same seed, so they see the same noise.
Your first moving goal showed no difference. What did you change?The ball moved slowly away at 0.12 m/s, and the robot (0.22 m/s) catches up whatever it believes. We made the ball cross the robot's path at 0.21 m/s, so predicting where it will be matters. The lesson is that the geometry decides whether a prediction helps.
What would break the goal estimator?A goal that turns or changes speed, because the line is extended straight. For a turn we would expect the fit to lag by about half its window (0.5 s), but we did not test a turning goal. A shorter window reacts faster and is noisier. A Kalman filter with an acceleration state would be the answer.
You said the controller only reads odometry. Why does it read the obstacle's pose from Gazebo?They are different quantities. The robot's own pose is estimated from its wheels, as on the real robot. The obstacle's pose stands in for what a tracker or a camera would provide. The proposal hands over the obstacle's future, so this is the stated assumption.
